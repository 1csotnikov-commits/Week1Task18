# Week1Task17 — MCP-сервер и MCP-клиент (Git + погода)

Минимальный учебный проект на Python с использованием официального
[MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk).
Демонстрирует, что MCP-соединение по транспорту **stdio** устанавливается,
клиент корректно получает список инструментов и умеет вызывать их вручную.
Дополнительно добавлены погодные инструменты (Open-Meteo) и команда агента
`/ask-weather`, передающая результат инструмента в LLM (DeepSeek).

## Назначение

- `mcp_server.py` — MCP-сервер с инструментами: `git_status`, `git_log`,
  `get_current_weather`, `get_forecast`.
- `client/` + `cli.py` — MCP-клиент с интерактивным режимом (`/help`, `/tools`,
  `/call`, `/weather`, `/ask-weather`, `/status`, `/reconnect`, `/exit`) и
  одноразовым режимом `--once`.
- `llm/` — провайдер LLM (DeepSeek) для команды `/ask-weather`.

Проект — **задел на будущие задания**: архитектура разделена так, чтобы позже
можно было легко добавить новые инструменты, отложенное/периодическое
выполнение и автономный tool use агента. Сейчас эти возможности не реализованы.

## Что такое MCP-сервер и MCP-клиент

- **MCP-сервер** — процесс, который предоставляет «инструменты» (функции) по
  протоколу Model Context Protocol. Здесь это обёртка над локальным `git` и
  погодным API Open-Meteo: сервер объявляет инструменты и выполняет их.
- **MCP-клиент** — процесс, который подключается к серверу, запрашивает список
  доступных инструментов и вызывает их. Здесь клиент сам запускает сервер как
  подпроцесс и общается с ним по stdio.

## Требования

- Python 3.10+
- Установленный `git`, доступный в `PATH`

## Установка зависимостей

```bash
pip install -r requirements.txt
```

В `requirements.txt` указаны `mcp>=2.0.0,<3.0` и `httpx` (HTTP-запросы к Open-Meteo и DeepSeek).

> Важно: используется **mcp 2.x**. В этой версии SDK класс `FastMCP` (из 1.x)
> переименован в `MCPServer`, поэтому сервер написан на актуальном API 2.x.

## Как задать GIT_REPO_PATH

Инструменты работают с репозиторием, путь к которому задаётся через переменную
окружения `GIT_REPO_PATH` (по умолчанию — текущая директория).

Windows (PowerShell):

```powershell
$env:GIT_REPO_PATH = "C:\путь\к\репозиторию"
```

Linux/macOS:

```bash
export GIT_REPO_PATH="/путь/к/репозиторию"
```

Также путь можно передать прямо в вызове `git_log` через параметр `repo_path`.

## Как запустить клиент

```bash
python cli.py
```

Одноразовый режим для быстрой проверки:

```bash
python cli.py --once
```

(имя, описание, JSON-схему входных параметров) и результат `git_status`:

```text

   Входные параметры (JSON-схема):

       },

=== Результат вызова git_status ===

=== git status --short ===
```

## Команды CLI

Все команды вводятся с префиксом `/`.

| Команда | Описание |
| --- | --- |
| `/help` | показать список всех команд с описанием |
| `/tools` | повторно запросить у MCP-сервера список инструментов и вывести его |
| `/call <tool_name> [args...]` | вызвать инструмент MCP вручную (например, `/call git_status` или `/call git_log limit=5`) |
| `/weather <city> [--days N] [--units metric\|imperial]` | показать погоду: текущую или прогноз на N дней |
| `/ask-weather <city> [вопрос]` | получить данные о погоде через MCP и передать их в LLM для ответа |
| `/status` | показать состояние MCP-соединения: подключение, имя сервера, версию протокола, инструменты, время последнего вызова |
| `/reconnect` | переустановить MCP-соединение: закрыть сессию, перезапустить сервер, initialize и заново получить инструменты |
| `/exit` (или `/quit`) | выйти из программы с корректным закрытием MCP-соединения |

Список команд формируется из единого источника (словарь `COMMANDS` в `cli.py`),
поэтому добавление новой команды автоматически отражается в `/help`.

### Примеры вызова инструментов

```text
> /call git_status
> /call git_log limit=3
> /call git_log limit=3 repo_path="C:\путь\к\репозиторию"
```

Аргументы задаются в виде `ключ=значение`; значения с пробелами заключаются в
двойные кавычки. Типы аргументов приводятся по JSON-схеме инструмента.

## Инструменты сервера

### `git_status`

Возвращает вывод `git status --short` и `git status -sb` для репозитория из
`GIT_REPO_PATH` (или текущей директории). Параметров нет.

### `git_log`

Возвращает список последних N коммитов: `hash`, `author`, `date`, `message`.

Параметры:

- `limit` (`int`, по умолчанию `10`) — сколько коммитов вернуть;
- `repo_path` (`str`, опционально) — путь к репозиторию (если не задан — берётся `GIT_REPO_PATH`).

### `get_current_weather`

Возвращает текстовое описание текущей погоды для города: температура, ветер,
влажность, осадки и краткое описание.

Параметры:

- `city` (`str`, обязательный) — название города (например, `Moscow`, `London`);
- `units` (`str`, по умолчанию `metric`) — `metric` (Цельсий, км/ч) или `imperial` (Фаренгейт, mph).

Пример через `/call`:

```text
> /call get_current_weather city=Moscow
```

### `get_forecast`

Возвращает текстовый прогноз на N дней: по каждому дню дата, температура
(min/max), осадки, ветер.

Параметры:

- `city` (`str`, обязательный);
- `days` (`int`, по умолчанию `3`, максимум `7`);
- `units` (`str`, по умолчанию `metric`).

Пример через `/call`:

```text
> /call get_forecast city=London days=5
```

## Погодные инструменты и используемый API

Погодные инструменты работают через бесплатный API [Open-Meteo](https://open-meteo.com/en/docs)
без API-ключа и регистрации:

- геокодинг (город → координаты): `https://geocoding-api.open-meteo.com/v1/search`;
- прогноз/текущая погода: `https://api.open-meteo.com/v1/forecast`.

Если город не найден, возвращается `Город "<city>" не найден.`; при недоступности
API — `Не удалось получить данные о погоде: <причина>`; при некорректных
параметрах (пустой город, `days > 7`) — `Некорректный параметр: <описание>`.

## Команды `/weather` и `/ask-weather`

### `/weather`

Синтаксис: `/weather <city> [--days N] [--units metric|imperial]`.

- без `--days` — текущая погода (`get_current_weather`);
- с `--days N` — прогноз на N дней (`get_forecast`).

Примеры:

```text
> /weather Moscow
> /weather London --days 5
> /weather Tokyo --units imperial
```

### `/ask-weather`

Синтаксис: `/ask-weather <city> [вопрос]`.

Команда вызывает погодный инструмент через MCP, получает данные и передаёт их
в LLM (DeepSeek) вместе с вопросом пользователя, после чего выводит ответ агента.

- если вопрос указан — промт: «Данные о погоде: `<данные>`. Вопрос пользователя:
  `<вопрос>`. Ответь, используя эти данные.»;
- если вопрос не указан — стандартный промт: «Опиши текущую погоду и дай
  рекомендацию по одежде.».

API-ключ DeepSeek берётся из переменной окружения `DEEPSEEK_API_KEY`; если он
не задан, выводится понятная ошибка.

```text
> /ask-weather Moscow Какая сегодня погода и что надеть?
```

## Пример сценария

Пользователь вводит:

```text
> /ask-weather Moscow Какая сегодня погода?
```

Приложение:

1. вызывает `get_current_weather("Moscow")` через MCP и получает данные;
2. формирует промт из данных о погоде и вопроса пользователя;
3. передаёт промт в LLM (DeepSeek) и выводит ответ агента.

## Обработка ошибок

Сервер не падает при ошибках: если `git` не установлен, путь не существует,
путь не является репозиторием или команда завершилась с ошибкой — инструмент
возвращает понятное сообщение об ошибке (на русском). Погодные инструменты
аналогично возвращают сообщения при недоступном API, ненайденном городе или
некорректных параметрах.

### Разделение слоёв (задел на будущее)

- `client/session.py` — только транспорт и сессия (`MCPSession`): запуск сервера,
  `initialize`, `list_tools`, `call_tool`. Никакой бизнес-логики.
- `client/logic.py` — высокоуровневая логика (`MCPApp`): решает, что вызывать,
  кэширует инструменты, форматирует результаты, готовит промты для LLM.
- `llm/provider.py` — изолированный вызов LLM (DeepSeek) для `/ask-weather`.
- `cli.py` — тонкая обёртка: разбор командной строки и цикл ввода.

## Что дальше (план расширения)

Сейчас реализован только минимальный каркас. Возможные следующие шаги:

1. **Новые инструменты** — достаточно добавить функцию с декоратором
   `@server.tool()` в `mcp_server.py`; клиент подхватит её автоматически.
2. **Отложенное/периодическое выполнение** — обернуть `MCPApp.call_tool` в
   планировщик (например, через `asyncio`); точки расширения уже заложены в
   `client/logic.py`.
3. **Автономный tool use агент** — цикл «решение → вызов инструмента → анализ
   результата» поверх `MCPApp.call_tool`, без изменений в `client/session.py`.
4. **Другие транспорты** — сейчас только stdio (по заданию); `MCPSession`
   изолирует параметры подключения, что упрощает переход на другие транспорты.
